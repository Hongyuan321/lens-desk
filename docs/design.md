# 技术方案与验收口径

## 从配置清单到交接记录

每套器材有唯一编号、组件名称与应有数量。借出时保存借用团队、发生时间和应还日期。归还时逐项输入实收数，缺口按“应有数量减累计实收”计算。每次成功操作在套装的事件列表中追加时间、经办人、动作及清点明细。

| 原状态 | 操作与条件 | 新状态 |
| --- | --- | --- |
| 可借 | 填写经办人、借用团队、有效应还日 | 借出中 |
| 借出中 | 归还时所有组件齐全 | 可借 |
| 借出中 | 任一组件缺失 | 待复核 |
| 待复核 | 登记依据，补齐一部分或确认缺口仍在 | 待复核 |
| 待复核 | 登记依据，确认所有组件齐套 | 可借 |

借出中且应还日早于浏览器本地日期时，界面显示已逾期。待复核保留原借用团队供跟进。齐套入库时清除当前借用信息，已发生的借还仍可在交接记录中查看。

## 实现与启动方式

浏览器表单将操作提交给纯函数 `LensDesk.change`。规则检查通过后，界面在同一 IndexedDB 读写事务中提交新状态和事件。若两张标签页操作同一条旧记录，提交时比较当前事件数量；旧表单被拒绝并重新读取台账。

原型使用 HTML、CSS 和原生 JavaScript，在浏览器本地计算。可选的 Node.js 服务只向回环地址提供项目静态资源。初始配置和样本生成逻辑见 `workflow.js`。部署到 GitHub Pages 时可直接从仓库根目录发布静态文件；访问者各自拥有独立数据。

## 权限与证据边界

值班员和复核人是演示中的业务角色，原型未对填写的姓名做身份验证。本地持有者可以清除或修改浏览器数据。跨设备共用时，需要由服务器验证身份，在数据库中校验角色并保存可追溯日志。

## 验收方法

运行仓库的规则测试后，按 README 完成浏览器演示。还可以同时打开两个标签页，对同一可借套装分别登记。先提交的一笔应保存，另一笔应收到记录已更新的提示。重新打开台账核对仅生成一笔新借出。

业务验收使用四份模拟材料。S1 确定数量上限，S2 验证借用归属，S3 验证两次清点，S4 判定是否可重新出借。现场试点后，应用真实且获准使用的材料重新校验流程假设。
